## 5. 다음 진행 순서

### 1단계: 실제 오류 URL 확보

Search Console → 페이지 색인 생성 → 사유별 행을 클릭해 **예시 URL 표가 보이는 상세 화면**에서 내보낸다. 상위 요약 화면의 내보내기를 반복하면 이번과 같은 요약만 나올 수 있다.

우선 필요한 상세 내보내기:

1. 서버 오류(5xx): 2개 URL와 최종 크롤링 시각.
2. Soft404: 1개 URL와 최종 크롤링 시각.
3. NOINDEX: 44개 URL와 최종 크롤링 시각.

추가 진단 자료:

- 발견됨-현재 미색인: 대표20~50개 URL만으로도 초기 원인 분류를 시작할 수 있음. 표의 다운로드 제한이 있으면 전체 보고서 건수와 실제 export 행 수를 구분.
- 크롤링됨-현재 미색인: 대표 URL/최종 크롤링 시각.
- 설정 → 크롤링 통계 보고서: 호스트 상태, 응답 코드 분포, 평균 응답 시간, Googlebot 요청 추이. 현재 제공되지 않았으므로 크롤링 용량 부족을 확정하지 않음.

### 2단계: P0 기술 오류 대조

대상 URL별 게시/삭제 상태 → 현재 HTTP/meta/header/canonical → Google 최종 크롤링 시각 → 해당 시각 배포/오류 로그 순서로 읽기 전용 대조한다. 공개 게시 기사에 재현되는 오류는 공통 원인 수정·회귀 테스트·안전한 배포 후 라이브 재검증한다. 삭제/미게시404와 내부 noindex는 유지한다.

### 3단계: 대규모 미크롤링 병목 확인

발견됨 URL 유형/게시일/카테고리/내부 링크 깊이/현재 status를 표본 분류한다. 서버 과부하가 실제 원인이면 기존 비용 보호를 유지하면서 응답 안정성을 개선한다. 기사 링크 접근성이 원인이면 실제 href 기반 SSR 페이지네이션을 검토한다. 가치/중복이 문제라면 근거·출처·자체 취재/분석을 보완한다. 단순 AI 문장 치환으로 독창성을 주장하지 않는다.

### 4단계: 효과 측정

주1회 같은 Search Console 필터·집계 범위로 색인/발견됨/크롤링됨 추이를 저장하고 대표 URL의 실제 URL Inspection 결과를 확인한다. sitemap 제출·IndexNow 성공·HTTP200을 Google 색인 완료로 취급하지 않는다. 색인 API 대량 호출, 삭제 기사 복원, 발행량 무조건 증대, 기사 lastmod를 의미 없이 갱신하는 방식은 사용하지 않는다.

- [Google 크롤링 오류 진단](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors): 미크롤링은 서버 용량·차단·발견/우선순위 등 원인별 조사 필요.

- [Google 페이지네이션·점진적 로딩](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading): 사용자 동작 버튼에 의존하지 않는 실제 href와 각 페이지 URL/canonical을 설계. 현재 더보기 구조의 개선 후보 근거이며 이번 미색인의 직접 원인 입증은 아님.
