# Phase 21-02 Plan: Registry Artifact Split Contract

**Date:** 2026-05-25
**Milestone:** v5.0 Registry Payload And API Weight Reduction
**Status:** Planned

## Goal

Define the generated artifact contract for summary, detail, and search-index registry data before changing runtime service reads.

## Scope

- Map current consumers of `public/generated/registry.json`, `page-registry.json`, category index, tag index, and shadcn `registry.json`.
- Define the minimum field set for:
  - component list summaries,
  - component detail responses,
  - component search index documents,
  - page registry and section-to-page lookups.
- Decide generated file names and compatibility behavior for the existing v1 API routes.
- Add a migration checklist for Phase 22 service adoption.

## Acceptance Criteria

- The contract identifies every current full-registry read that must move to a lighter artifact.
- The contract documents fields that must remain stable for `/api/v1/components`, `/api/v1/components/search`, and `/api/v1/components/[id]`.
- Phase 22 can implement the split without revisiting high-level API semantics.

## Verification Plan

- Review `src/lib/registry.service.ts`, `src/lib/search.service.ts`, `src/lib/page-registry.service.ts`, and API route consumers.
- Run `pnpm check:registry-payload` after any generated artifact contract change.
- Keep `pnpm check:planning` green after updating roadmap/state.
